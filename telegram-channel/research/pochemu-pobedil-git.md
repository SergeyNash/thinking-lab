# Почему победил Git

Статус: исследуем  
Начато: 29 июня 2026 года  
Последнее обновление: 9 сентября 2026 года  
Возможный формат: сначала Telegram-пост; эссе — только после усиления источников

## Сигнал и вопрос

Git стал устойчивым стандартом, но объяснения «он быстрый», «его создал Линус» или «его продвинул GitHub» не объясняют всё. Почему его модель так хорошо совпала с реальной работой разработчиков?

## Граница системы

Сначала рассматриваем Git как модель контроля версий и примитив совместной работы. GitHub считаем усилителем распространения, но проверяем, не недооценена ли его роль.

## Контекст и ограничения

До Git существовали CVS, Subversion, Perforce, BitKeeper, Mercurial, Bazaar, Monotone и другие системы.

Начальные ограничения разработки ядра Linux:

- распределённые участники;
- большой поток изменений;
- разные уровни доверия;
- потребность в локальной работе;
- высокая цена повреждения истории;
- скорость и асинхронная координация.

Этот раздел пока основан на концептуальном и историческом наброске. Нужны первичные источники.

## Конкурирующие объяснения

- Git победил из-за скорости.
- Решающим был авторитет Линуса Торвальдса.
- Победу обеспечил GitHub.
- Любая распределённая VCS была бы лучше централизованной.
- Модель Git точнее других систем соответствовала реальному поведению разработки.
- После распространения сработали экосистема, привычка и стоимость переключения.

## Механизм и структура стоимости

Git сделал дешевле:

- ветвление;
- локальные commits;
- параллельную работу;
- просмотр и сравнение истории;
- выбрасывание неудачного эксперимента;
- восстановление после ошибки;
- асинхронную координацию.

Кандидат на механизм: команда чаще пробует и работает меньшими шагами, когда промежуточное состояние, ошибка и возврат перестают быть дорогими событиями.

## Факты и источники

Текущий уровень: концептуальный и исторический набросок, ещё не source-backed исследование.

Нужно проверить:

- хронологию конфликта BitKeeper и появления Git;
- исходные design goals Git;
- сравнение с Mercurial, Bazaar, Monotone, SVN, CVS и BitKeeper;
- роль GitHub в распространении и стандартизации workflow;
- какие свойства были уникальны для Git, а какие общими для DVCS.

## Возражения и контрпримеры

- Git сложен для новичков и не обладает очевидной ментальной моделью.
- Другие DVCS тоже снижали цену ветвления и локальной работы.
- Маленькой централизованной команде часть сложности Git может быть не нужна.
- Скорость и целостность истории могли быть важнее экспериментов.
- Архитектурное соответствие не объясняет распространение без экосистемы.

## Возможный принцип

Поведение меняется, когда проба, ошибка, обучение и восстановление становятся дешевле, чем попытка заранее избежать всей неопределённости.

Более узкая версия: Git снизил цену эксперимента и восстановления в среде, где параллельная работа, ошибки и частичное доверие являются нормой.

## Перенос и его границы

Сильный возможный перенос:

- продуктовые эксперименты с быстрой обратной связью;
- безопасные paved roads и secure defaults;
- AI-workflows с evaluation и review.

Более слабый перенос:

- эксперименты с организационными процессами;
- личные системы мышления и письма.

Граница: в организации rollback имеет политическую и эмоциональную цену. В AI генерация может быть дешёвой, а проверка — дорогой. Необратимые решения и слабая обратная связь ломают принцип.
