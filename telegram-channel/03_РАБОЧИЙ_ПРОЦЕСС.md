# Рабочий процесс

Этот файл описывает, как мы ведём канал в диалоге. Сергей может принести сырую мысль, голосовую расшифровку, ссылку, чужой текст, готовый черновик или вопрос. Заполнять анкету не требуется.

## Один пост — один чат

Каждый новый пост разрабатывается в отдельном чате внутри проекта. Чат становится рабочим пространством одного материала: от первой мысли до финальной версии.

В одном чате можно:

- покрутить исходное наблюдение;
- провести исследование;
- спорить с тезисом и менять направление;
- готовить несколько версий текста;
- обсуждать иллюстрацию;
- довести пост до публикации и разобрать реакцию.

Не переносим в этот чат работу над другим постом. Если из разговора родилась самостоятельная тема, добавляем её в банк тем и продолжаем в новом чате.

Общая память хранится не в конкретном чате, а в папке канала. Поэтому в начале работы я проверяю общие правила, банк тем, реестр и связанные исследования. После значимого результата обновляю их. Новый чат не должен начинать содержательную работу с нуля.

Название чата желательно формулировать по рабочему тезису или вопросу, а не по широкой теме:

- хорошо: `Почему большой промпт смешивает разные типы знания`;
- слабо: `Пост про AI`;
- хорошо: `У B2B-продукта два клиента`;
- слабо: `Продуктовый пост`.

Один чат может закончиться решением не публиковать материал. Это тоже результат: сохраняем полезное исследование или причину отказа, чтобы не повторять путь позже.

## Что я делаю при входе

1. Определяю, что принесено: сигнал, тема, исследование, черновик или правка.
2. Проверяю банк тем, исследования и реестр постов, чтобы не потерять прошлую работу.
3. Извлекаю из сообщения известные параметры: замысел, аудиторию, формат, глубину и ограничения.
4. Задаю только те вопросы, ответы на которые реально изменят направление работы.
5. Предлагаю следующий маленький шаг, а не запускаю тяжёлый процесс автоматически.

## Основной поток

```text
мысль / ссылка / ситуация
→ формулировка вопроса
→ выбор глубины
→ исследование или разбор опыта
→ решение о формате
→ содержательный каркас
→ черновик
→ критика аргумента
→ редактура голоса
→ согласование
→ публикация
→ фиксация результата и новых вопросов
```

Переходы могут возвращаться назад. Если во время редактуры становится видно, что причинная связь слабая, возвращаемся к исследованию.

## Режимы работы

### «Покрутим мысль»

Не пишем пост сразу. Разбираем наблюдение, возможные объяснения, механизм и конфликт. Результат — формулировка идеи и следующие вопросы.

### «Исследуй»

Согласуем глубину, проверяем источники и сохраняем рабочую заметку. Пост появляется только при достаточной готовности.

### «Напиши пост»

Если основание уже есть, собираем каркас и черновик. Если его нет, коротко показываем пробел и предлагаем быстрый исследовательский проход.

### «Отредактируй мой текст»

Сначала сохраняем авторскую мысль и факты. Затем правим причинность, структуру, русский язык и ритм. Новые факты без проверки не добавляем.

### «Подготовь иллюстрацию»

Сначала согласуем функцию и визуальную идею. После согласования создаём изображение. Иллюстрация должна дополнять мысль, а не повторять заголовок.

## Состояния темы

- `сигнал` — есть наблюдение, но вопрос ещё не найден;
- `исследуем` — сформулирован вопрос и собирается основание;
- `созрело` — понятны механизм, ограничение и возможный вывод;
- `в черновике` — существует текст;
- `готово` — согласован финальный текст;
- `опубликовано` — добавлены дата и ссылка;
- `отложено` — сохранена причина паузы;
- `отклонено` — зафиксировано, почему идея не выдержала проверки.

## Где что хранится

- `04_БАНК_ТЕМ.md` — короткий индекс всех направлений;
- `research/` — содержательные заметки и источники;
- `drafts/` — тексты в работе;
- `published/` — только фактически опубликованные версии;
- `05_РЕЕСТР_ПОСТОВ.md` — статусы, даты, связи и обратная связь;
- `inbox/` — необработанные материалы;
- `assets/` — иллюстрации и связанные с ними описания;
- `sync/` — состояние GitHub и карта экспорта.

## После каждого значимого шага

- новая идея попадает в банк тем;
- исследование получает отдельную заметку;
- черновик сохраняется отдельным файлом;
- после публикации финальная версия переносится в `published/`;
- реестр получает дату, ссылку и реакцию аудитории;
- сильный контрпример или провал остаётся в исследовании, чтобы не повторять ошибку.

Перед завершением работы над постом я проверяю, что результат чата вынесен в общую папку. Иначе знания останутся заперты внутри одной переписки и следующий чат их не увидит.

## Правило автономности

Для обычного поста достаточно прочитать паспорт канала, правила письма, рабочий процесс и связанные материалы по теме. GitHub для ежедневной работы не нужен.

## Обновление GitHub

По команде «подготовь обновление репозитория»:

1. Проверяем текущий commit репозитория против `sync/SOURCE_STATE.md`.
2. Показываем изменения, сделанные в GitHub после последней синхронизации.
3. Формируем экспорт по `sync/REPO_MAP.md`.
4. Создаём отдельную ветку `sync/telegram-workspace-YYYY-MM-DD`.
5. Делаем commit и pull request.
6. Не удаляем старые файлы автоматически и не сливаем PR без явной команды.
